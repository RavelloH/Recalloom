# 快照导出、校验与恢复

Recalloom 使用 recalloom-snapshot-v4 格式，分页保存文档、元数据、版本历史、标签定义与关联（稳定 ID、别名、颜色和描述）、人工关系、任务全局顺序和 Wiki 路径到 UUID 的持久绑定（包括目标已删除的绑定）。导入后按整批记录重建 Wiki 引用投影。旧 v2/v3 快照仍可导入，但其中没有保存的任务顺序与路径绑定无法追溯恢复。快照可能包含敏感的历史正文，应按敏感数据妥善存放。

## 导出

1. 调用 export_snapshot，不传 cursor；可设置 limit 控制每页返回的记录数（最多 5）。
2. 读取返回的 page.nextCursor，依次获取后续页面，直到为空。
3. 保持原始顺序与内容，收集所有页面为 {pages:[...all pages...]}。
4. 记录并核对变更水位、任务 orderVersion 及 SHA-256；如导出过程中数据变化导致快照失效，应重新导出，不能把不同状态的页面拼接成合法备份。

## 验证和导入

import_snapshot 接收**完整** bundle={pages:[...]}，而不是其中某一页。默认 dryRun=true，只进行格式、哈希、冲突及规模校验，不修改当前数据。

只有在用户明确授权真实导入、并已充分检查覆盖/冲突风险后，才将 dryRun=false；服务端会以原子性方式导入，并保护已有 UUID 和路径，且有限制条件（最多 300 条记录、2,000 个文件夹、3,000 条人工关系、100 页与 700 条事务语句，完整 bundle 序列化后的 JSON 不超过 6,000,000 个 UTF-16 代码单元）。现有 UUID 或路径冲突会被拒绝；不会覆盖原库。空库恢复时，v4 完整保留任务的全局位置；向已有任务的库合并时，按导入任务的原有相对顺序追加到末尾。验证期间目标库发生变化会拒绝整批导入，需要重新开始。切勿假设可以无条件覆盖整个知识库。

## 与常规版本恢复的区别

- 恢复单条记录的旧版本：使用 restore_record，并提供 expectedRevision。
- 检查历史正文差异：使用 version_history、read_record(revision)、diff_revisions。
- 跨实例/整库快照迁移：使用 export_snapshot/import_snapshot。

快照导入并不是一项自动后台任务，也不是编辑 Markdown 的替代操作。涉及风险的真实写入应先 dryRun 和人工确认。
